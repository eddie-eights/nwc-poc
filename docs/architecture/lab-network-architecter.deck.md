# この lab は何をする場所か

本物のスイッチ OS を 6 台動かし、テスト用のパケットを流し、起きたことを AWS に集めます。

## この lab は、パケットを流し、運び、起きたことを見る場所です

::: columns

**流す: TRex**

- ネットワークに負荷をかけるための装置
- 本番のサーバーの代わりに、大量のパケットを作って流す

**運ぶ: スイッチ 6 台**

- Nokia の本物のスイッチ OS（SR Linux）をコンテナで動かす
- 設定は本物と同じ。この資料はここの話

---

**見る: AWS に集める**

- スイッチが出す「回線が切れた」などの通知やログを集める
- 障害が起きたら気づける仕組みを作るのが PoC の本題

:::

::: notes
- 6 台は dc1-spine-01/02、dc1-s-leaf-01/02、dc1-a-leaf-01/02。TRex は dc1-trex-01（app/containerlab/gen_lab.py）。
- SR Linux の機種は ixr-d2l（ライセンス不要）。
:::

## 登場するのは、中央の spine 2 台、末端の leaf 4 台、その先の利用者とサーバーです

- 中央: dc1-spine-01、dc1-spine-02
- 末端（WAN 側）: dc1-s-leaf-01、dc1-s-leaf-02。先には利用者や外のネットワーク（WAN）がつながる
- 末端（DC 側）: dc1-a-leaf-01、dc1-a-leaf-02。先にはサーバーがつながる
- どの leaf も spine 2 台の両方につながる（ケーブル 8 本）。leaf 同士は直接つながない
- lab には利用者もサーバーもいないので、末端のケーブル 4 本は負荷試験用の装置 dc1-trex-01（eth1 〜 eth4）につないである

::: notes
- spine と leaf は全組み合わせを結ぶ。spine 側のポートは ethernet-1/<leaf の番号>、leaf 側のポートは ethernet-1/<spine の番号>。
- TRex は負荷試験のときだけ、利用者とサーバーの代わりにパケットを流す（app/containerlab/gen_lab.py）。
- 図は Claude のデッキ（https://claude.ai/artifact/3DtfxGFkTehxxwRpHRcB8u）の 3 枚目にある。
:::

## spine は IP で運ぶだけ、leaf はスイッチとルーターの両方を務めます

::: columns

**spine（中央）**

- 末端のケーブルはつながっていない
- leaf から来たパケットを、宛先の IP アドレスを見て別の leaf へ渡す
- あとで出てくる「どの MAC アドレスがどこにいるか」の取りまとめ役も担う

---

**leaf（末端）**

- 利用者やサーバー側のポートでは、MAC アドレスを見るスイッチとして動く
- spine 側のポートでは、IP で通信するルーターとして動く
- 2 つの顔をつなぐ「包む・ほどく」も leaf の仕事

:::

6 台とも同じ SR Linux で、どちらの動きもできます。spine と leaf の違いは機種ではなく、どこに置いてどう設定したかです。

## leaf が WAN 側と DC 側に分かれているのは、本物のデータセンターの形だからです

- 本物では、利用者や外のネットワークがつながる leaf（WAN 側、s-leaf）と、サーバーがつながる leaf（DC 側、a-leaf）が分かれている
- この PoC は監視が本題なので、「DC 側の leaf で回線が切れた」と本物と同じ役割の名前で出せるように分けている
- 4 台の設定は同じ。仮に 4 台とも DC 側にしても、通信や試験は変わらない
- それぞれ 2 台ずつあるのは、本物と同じく 1 台が止まっても通信が続く形（冗長構成）にするため。片方の回線を落として、監視が気づくかを安全に試せる
- 組になる 2 本のケーブルを別々の leaf につなぐので、パケットは必ず leaf → spine → leaf と幹線を通り、3 つの仕組みを全部通して確かめられる

::: notes
- a-leaf / s-leaf の a と s の意味は依頼の名前のままで、確かめていない（docs/cycles/011-lab-isis-trex-x86/design.md の未確定事項 1）。
- TRex の組は trex/trex_cfg.yaml.in（port 0 ↔ 1 が s-leaf の組、port 2 ↔ 3 が a-leaf の組）。mac-vrf の ecmp は 2。
:::

# 先に知っておく言葉

ポートの名前、アドレスの 2 種類、LAN の中と外。

## 言葉 1: 同じポートでも、どの立場から見るかで名前が違います

| TRex の番号 | Linux での名前 | つながっている先 | このポートの IP アドレス |
|---|---|---|---|
| port 0 | eth1 | dc1-s-leaf-01 の ethernet-1/3 | 10.100.0.11 |
| port 1 | eth2 | dc1-s-leaf-02 の ethernet-1/3 | 10.100.0.12 |
| port 2 | eth3 | dc1-a-leaf-01 の ethernet-1/3 | 10.100.0.13 |
| port 3 | eth4 | dc1-a-leaf-02 の ethernet-1/3 | 10.100.0.14 |

- **eth1**: Linux が付ける名前。TRex は Linux のコンテナなので、eth0 が管理用、eth1 〜 eth4 が leaf へつないだ 4 本
- **ethernet-1/3**: スイッチ（SR Linux）側の名前。1 枚目の基板の 3 番ポート。1/1 と 1/2 は spine へ、1/3 は TRex へ
- **port 0**: TRex のソフトが数える番号。0 から始まるので eth1 が port 0

## 言葉 2: アドレスには、LAN の中だけで使う MAC と、LAN をまたぐ IP の 2 種類があります

::: columns

**MAC アドレス**

- ポートごとに最初から付いている 12 桁の番号
- 使えるのは同じ LAN の中だけ
- スイッチは「この MAC アドレスはどのポートの先か」の表（MAC アドレステーブル）で、送り出すポートを決める

---

**IP アドレス**

- あとから人が割り当てる 4 つの数字
- LAN をまたいで届く。ルーターが宛先の IP アドレスを見て、次に渡す相手を決める
- TRex のポートは 10.100.0.11 〜 .14、スイッチ本体は 10.255.x.y

:::

## 言葉 3: LAN の中は MAC アドレスで届き、LAN をまたぐと IP アドレスで届きます

::: columns

**同じ LAN の中（L2）**

- 送る側は「この IP の MAC アドレスは何か」と LAN 全体に聞く（ARP）
- 返ってきた MAC アドレスを宛先にして送る
- スイッチが MAC アドレステーブルを見て送り出す

---

**LAN をまたぐ（L3）**

- ルーターが宛先 IP を見て、経路表に従って次へ渡す
- MAC アドレスは区間ごとに書き換わる

:::

この lab のスイッチ同士は IP で運ぶので、そのままでは leaf 1 と leaf 2 のポートは同じ LAN になりません。

# やりたいこと

leaf 1 につないだケーブルと leaf 2 につないだケーブルを、同じ LAN に見せたい。

## 間は IP で運ぶので、3 つの仕組みが要ります

- 間にあるのは IP で運ぶスイッチ。MAC アドレスだけでは届かない
- 仕組み 1: 経路を交換する（IS-IS）
- 仕組み 2: どの MAC アドレスがどこにいるかを共有する（BGP EVPN）
- 仕組み 3: 封筒に入れて運ぶ（VXLAN）

## 仕組み 1: IS-IS は、スイッチ同士が経路表を自動で作り合う仕組みです

スイッチ同士は IP で通信するので「どのスイッチへはどのポートから出るか」の経路表が要ります。人が書かずに自動で作る仕組みが IS-IS です。

- 隣に知らせる: 「自分は誰で、隣に誰がいるか」を隣へ送る。6 台が同じ情報を持つまで繰り返す
- 地図を作る: 集まった情報で全体の地図を作り、「どこへは最短でどのポートか」を経路表に書く
- 回線が切れたら: 全員が地図を作り直す。spine が 2 台あるので、もう一方を通る経路に切り替わる
- 交換するのは主にスイッチ本体の IP アドレス（ループバック）。ポートが 1 本切れても消えない
- これで leaf からほかの leaf 本体へ IP で送れる。この土台の層を underlay と呼ぶ

::: notes
- ループバック: spine は 10.255.0.1/.2、WAN 側 leaf は 10.255.1.1/.2、DC 側 leaf は 10.255.2.1/.2。
- IS-IS は level 2、point-to-point、インスタンス名 main（app/containerlab/gen_lab.py）。
- この段階ではまだ TRex のパケットは運べない。運ぶための土台ができただけ。
:::

## 仕組み 2: BGP EVPN は、leaf 同士が「どの MAC アドレスがどこにいるか」を教え合う仕組みです

leaf は、自分の TRex 側のポートで見た MAC アドレスしか知りません。「その MAC アドレスは向こうの leaf の先にいる」と知るために、MAC アドレステーブルの中身を教え合います。

- BGP: ルーター同士が「こういう宛先を知っている」と知らせ合う仕組み。インターネットでも使われている
- EVPN: その BGP で、IP の経路ではなく MAC アドレスの居場所を知らせる使い方
- 知らせる内容: 「MAC アドレス ◯◯ は私（leaf 10.255.2.1）の先にいます」。受け取った leaf は 10.255.2.1 へ送ればよいと分かる
- spine が取りまとめ役: leaf は spine にだけ知らせ、spine が全 leaf に配り直す（ルートリフレクタ）。spine 2 台が同じ役割
- 目印の番号: 全員が同じ番号 65100（AS 番号）を名乗り、共有する LAN に 100 という番号を付ける

::: notes
- iBGP AS 65100、EVPN だけ、ループバック同士で張る。spine が route reflector で cluster-id は自分のループバック。
- mac-vrf macvrf-100: EVI 100、VNI 100、route-target 65100:100。
:::

## 仕組み 3: VXLAN は、leaf がパケットをまるごと IP の封筒に入れて運ぶ仕組みです

TRex のパケットは MAC アドレス宛てなので、IP で運ぶ spine はそのままでは扱えません。leaf がパケットをまるごと IP の封筒に入れ（カプセル化）、宛先は仕組み 2 で分かった向こうの leaf のアドレスにします。

| 封筒の部分 | 書いてあること | 意味 |
|---|---|---|
| 封筒の宛先 IP | 10.255.2.1 → 10.255.2.2 | leaf 本体から leaf 本体へ |
| 封筒の種類 | UDP 4789 | VXLAN だと分かる番号 |
| LAN の番号 | VNI 100 | どの LAN のパケットか |
| 中身 | 10.100.0.13 → 10.100.0.14 | TRex の元のパケット。MAC アドレスも含めてそのまま |

- 包む側の leaf: 宛先の MAC アドレスがいる leaf のアドレスへ、封筒に入れて送る
- 途中の spine: 封筒の宛先 IP アドレスしか見ない。経路表どおりに隣へ渡すだけ
- ほどく側の leaf: 封筒を開け、VNI 100 のパケットだと確かめて TRex 側のポートへ送り出す
- この封筒の層を overlay（オーバーレイ）と呼ぶ

## 1 つのパケットは、TRex → leaf → spine → leaf → TRex と 5 段階で届きます

- 1 TRex が送る: port 2 から、宛先 MAC アドレスを port 3 のものにしたパケットを送る。普通の LAN と同じ動き
- 2 a-leaf-01 が包む: 「その MAC アドレスは 10.255.2.2 の先」と知っているので、封筒に入れて送る
- 3 spine が運ぶ: 封筒の宛先 10.255.2.2 を経路表で引き、a-leaf-02 へ渡す。封筒の中身は見ない
- 4 a-leaf-02 がほどく: 封筒を開け、中のパケットを ethernet-1/3 から送り出す
- 5 TRex が受け取る: 送られたときと同じ形で port 3 に届く。間に 3 台いたことは分からない

::: notes
- spine は 2 台どちらを通っても同じ長さなので、leaf がパケットの組ごとに振り分ける（ECMP）。1 本切れればもう一方だけになる。
- 相手の MAC アドレスをまだ知らないとき（ARP）は LAN 全体宛てなので、leaf は同じ LAN 番号を持つ全 leaf に封筒を 1 通ずつ送る（ingress replication）。
- port 0 ↔ port 1 は s-leaf-01 と s-leaf-02 の間で同じ動きをする。
:::

# 見る・替える・まとめ

スイッチが起きたことを知らせる 3 つの経路、SR-MPLS への差し替え、覚えておくこと。

## 6 台のスイッチで起きたことは、3 つの経路で lab の外へ送られます

| 経路 | 送られるもの | 受け取る側 |
|---|---|---|
| SNMP トラップ | 「ポートが落ちた」などの出来事。起きた瞬間にスイッチが送る | Telegraf がキューへ |
| syslog | スイッチのログ 1 行ずつ。これもスイッチが送る | syslog-ng がキューへ |
| gNMI | 通信量や BGP の状態。外から定期的に取りに行く | gnmic がキューへ |

- キュー: 届いたものを順にためて、読む側が自分のペースで取り出す場所（AWS の MSK）
- そのあと: キューから取り出して整え、検索・グラフ・保存・アラートの仕組みへ配る
- スイッチは決まった宛先に送るだけで、lab の EC2 が AWS の受け口へ転送する

::: notes
- SNMP trap 162/udp → Telegraf → MSK の traps。syslog 5140/udp → syslog-ng → logs。gNMI 57400 ← gnmic → gnmi（状態の変化）と metrics（60 秒ごとの数字）。
- 宛先 203.0.113.1 は lab の EC2 で、iptables の DNAT で NLB へ転送する（docs/pipeline.md）。
- 後ろは Spark → OpenSearch / Prometheus / S3 Tables / Splunk、アラートは SNS → Lambda → Neptune。
:::

## 依頼にあった SR-MPLS は、機種とライセンスの都合で VXLAN に置き換えています

2026-10-08 の依頼では「ISIS / SR-MPLS」の構成が挙がっていました。SR-MPLS は仕組み 3 の封筒を別の種類にする話で、仕組み 1 と 2 はそのまま使います。

| 項目 | いま: VXLAN | 依頼: SR-MPLS |
|---|---|---|
| 封筒 | IP（宛先は leaf のアドレス） | 短い番号（ラベル）を先頭に貼る |
| spine の仕事 | 経路表を引く普通の IP ルーター | ラベルを見て回すだけ |
| 機種 | ixr-d2l（ライセンス不要） | ixr-6e とライセンスが要る |

- 手元に機種とライセンスがないので、まず VXLAN で全体を通すと「lab を IS-IS と TRex で組む（011）」で決めた
- 替えるときは、生成スクリプトで機種とライセンスを指定し直し、leaf の「封筒に入れる」設定を替える
- スイッチの並び・ケーブル・IS-IS・BGP EVPN・TRex・監視の 3 経路は変わらない

::: notes
- docs/cycles/011-lab-isis-trex-x86/design.md。gen_lab.py の type を ixr-6e にし license を付ける。
- Neptune の構成図は vtep を SR のラベルと読み替えるだけで、id と edge は変えない（docs/data-stores.md）。
:::

## 覚えておくことは 3 つです

- スイッチ同士は IP で運ぶ。だから leaf 1 と leaf 2 の TRex 側のポートは、そのままでは同じ LAN にならない
- IS-IS で経路表を作り、BGP EVPN で MAC アドレスの居場所を教え合い、VXLAN の封筒で運ぶ。leaf が包み、spine が運び、leaf がほどく
- SR-MPLS は封筒の種類が違うだけ。機種とライセンスがそろったら封筒を替える。監視の 3 経路はそのまま
