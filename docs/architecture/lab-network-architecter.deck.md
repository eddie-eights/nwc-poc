# この lab は何をする場所か

本物のスイッチ OS を 6 台動かし、テスト用のパケットを流し、起きたことを AWS に集めます。

## この lab は、パケットを流し、運び、起きたことを見る場所です

::: columns

**流す: TRex**

- ネットワークに負荷をかけるための装置
- 本番のサーバーの代わりに、大量のパケットを作って流す

**運ぶ: スイッチ 6 台**

- Nokia の本物のスイッチ OS（SR Linux）をコンテナで動かす
- 設定は本物と同じ。この資料はここの話

---

**見る: AWS に集める**

- スイッチが出す「回線が切れた」などの通知やログを集める
- 障害が起きたら気づける仕組みを作るのが PoC の本題

:::

::: notes
- 6 台は dc1-spine-01/02、dc1-s-leaf-01/02、dc1-a-leaf-01/02。TRex は dc1-trex-01（app/containerlab/gen_lab.py）。
- SR Linux の機種は ixr-d2l（ライセンス不要）。
:::

## 登場するのは、中央の spine 2 台、末端の leaf 4 台、その先の利用者とサーバーです

- 中央: dc1-spine-01、dc1-spine-02
- 末端（WAN 側）: dc1-s-leaf-01、dc1-s-leaf-02。先には利用者や外のネットワーク（WAN）がつながる
- 末端（DC 側）: dc1-a-leaf-01、dc1-a-leaf-02。先にはサーバーがつながる
- どの leaf も spine 2 台の両方につながる（ケーブル 8 本）。leaf 同士は直接つながない
- LAN の境目は leaf。末端の 4 本は同じ 1 つの LAN（10.100.0.0/24）で MAC アドレスで届き、spine と leaf の間はケーブルごとに別の IP ネットワーク（172.16.x.y/31）
- lab には利用者もサーバーもいないので、末端のケーブル 4 本は負荷試験用の装置 dc1-trex-01（eth1 〜 eth4）につないである

::: notes
- spine と leaf は全組み合わせを結ぶ。spine 側のポートは ethernet-1/<leaf の番号>、leaf 側のポートは ethernet-1/<spine の番号>。
- TRex は負荷試験のときだけ、利用者とサーバーの代わりにパケットを流す（app/containerlab/gen_lab.py）。
- 図は Claude のデッキ（https://claude.ai/artifact/3DtfxGFkTehxxwRpHRcB8u）の 3 枚目にある。
:::

## spine は IP で運ぶだけ、leaf はスイッチとルーターの両方を務めます

::: columns

**spine（中央）**

- 末端のケーブルはつながっていない
- leaf から来たパケットを、宛先の IP アドレスを見て別の leaf へ渡す
- あとで出てくる「どの MAC アドレスがどこにいるか」を、leaf から受け取ってほかの leaf へ配り直す役（ルートリフレクタ）も担う

---

**leaf（末端）**

- 利用者やサーバー側のポートでは、MAC アドレスを見るスイッチとして動く
- spine 側のポートでは、IP で通信するルーターとして動く
- 元のパケットに IP のヘッダーを付け足す・外す処理（仕組み 3）も leaf の仕事

:::

6 台とも同じ SR Linux で、どちらの動きもできます。spine と leaf の違いは機種ではなく、どこに置いてどう設定したかです。

## leaf が WAN 側と DC 側に分かれているのは、本物のデータセンターの形だからです

- 本物では、利用者や外のネットワークがつながる leaf（WAN 側、s-leaf）と、サーバーがつながる leaf（DC 側、a-leaf）が分かれている
- この PoC は監視が本題なので、「DC 側の leaf で回線が切れた」と本物と同じ役割の名前で出せるように分けている
- 4 台の設定は同じ。仮に 4 台とも DC 側にしても、通信や試験は変わらない
- それぞれ 2 台ずつあるのは、本物と同じく 1 台が止まっても通信が続く形（冗長構成）にするため。片方の回線を落として、監視が気づくかを安全に試せる
- 組になる 2 本のケーブルを別々の leaf につなぐので、パケットは必ず leaf → spine → leaf と幹線を通り、3 つの仕組みを全部通して確かめられる

::: notes
- a-leaf / s-leaf の a と s の意味は依頼の名前のままで、確かめていない（docs/cycles/011-lab-isis-trex-x86/design.md の未確定事項 1）。
- TRex の組は trex/trex_cfg.yaml.in（port 0 ↔ 1 が s-leaf の組、port 2 ↔ 3 が a-leaf の組）。mac-vrf の ecmp は 2。
:::

# 先に知っておく言葉

ポートの名前、アドレスの 2 種類、LAN の中と外。

## 言葉 1: 同じポートでも、どの立場から見るかで名前が違います

| TRex の番号 | Linux での名前 | つながっている先 | このポートの IP アドレス |
|---|---|---|---|
| port 0 | eth1 | dc1-s-leaf-01 の ethernet-1/3 | 10.100.0.11 |
| port 1 | eth2 | dc1-s-leaf-02 の ethernet-1/3 | 10.100.0.12 |
| port 2 | eth3 | dc1-a-leaf-01 の ethernet-1/3 | 10.100.0.13 |
| port 3 | eth4 | dc1-a-leaf-02 の ethernet-1/3 | 10.100.0.14 |

## eth1、ethernet-1/3、port 0 は、どれも同じ 1 つの物理ポートです

- 物理ポートは、ケーブルが刺さっている口のこと。Linux、スイッチ、TRex のソフトが別の名前で呼んでいるだけ
- eth1 は Linux の名前。eth0 は管理用
- ethernet-1/3 はスイッチの名前。1 枚目の基板の 3 番ポート。1/1 と 1/2 は spine へ
- port 0 は TRex が 0 から数えた番号
- localhost:8000 の 8000 のようなポート番号（アプリを区別する番号）とは別物

## 言葉 2: アドレスには、LAN の中だけで使う MAC と、LAN をまたぐ IP の 2 種類があります

::: columns

**MAC アドレス**

- ポートごとに最初から付いている 12 桁の番号
- 使えるのは同じ LAN の中だけ
- スイッチは「この MAC アドレスはどのポートの先か」の表（MAC アドレステーブル）で、送り出すポートを決める

---

**IP アドレス**

- あとから人が割り当てる 4 つの数字
- LAN をまたいで届く。ルーターが宛先の IP アドレスを見て、次に渡す相手を決める
- TRex のポートは 10.100.0.11 〜 .14、スイッチ本体は 10.255.x.y

:::

## 言葉 3: 同じ LAN の中では、MAC アドレスで届きます（PC A → スイッチ → PC B）

- 1 A が LAN 全体に「10.100.0.14 の MAC アドレスは何か」と聞く（ARP）
- 2 B が「bb」と答える。A はそれを覚える
- 3 A は宛先 MAC アドレスを bb にして送る
- 4 スイッチは MAC アドレステーブルで「bb はポート 2」と引き、ポート 2 へ送り出す

| スイッチの MAC アドレステーブル | 送り出すポート |
|---|---|
| MAC aa（PC A、10.100.0.13） | ポート 1 |
| MAC bb（PC B、10.100.0.14） | ポート 2 |

## 言葉 3 の続き: LAN をまたぐときは、ルーターが IP アドレスを見て次へ渡します（PC A → R1 → R2 → PC C）

- 1 A は宛先 IP を 10.200.0.5、宛先 MAC アドレスを R1 にして送る
- 2 R1 は経路表で「10.200.0.0/24 は R2 へ」と引き、宛先 MAC アドレスを R2 に書き換えて渡す
- 3 R2 は C が自分の LAN にいると分かり、宛先 MAC アドレスを C にして届ける
- 4 IP アドレスは最後まで変わらない。MAC アドレスは区間ごとに変わる

| R1 の経路表（ルーティングテーブル） | 次に渡す相手 |
|---|---|
| 10.100.0.0/24 | 自分の LAN。直接届ける |
| 10.200.0.0/24 | R2 |

::: notes
- この lab では spine と leaf の間がこの形（IP で運ぶ）なので、a-leaf-01 のポートと a-leaf-02 のポートは、そのままでは同じ LAN にならない。
:::

# やりたいこと

a-leaf-01 につないだケーブルと a-leaf-02 につないだケーブルを、同じ LAN に見せたい。

## やりたいことは、a-leaf-01 のポートと a-leaf-02 のポートを同じ LAN にすることです

TRex の port 2 から port 3 へ、宛先 MAC アドレスを port 3 にしたパケットを送ると、1 台ずつ次のことが起きます。

| 通る場所 | 起きること |
|---|---|
| TRex port 2 | 宛先 MAC アドレス = port 3 で送る。LAN の中のつもり |
| dc1-a-leaf-01 | 困る 1: MAC アドレステーブルに port 3 がない |
| dc1-spine-01 / 02 | 困る 2: MAC アドレスを見ない。IP の経路表しか持たない |
| dc1-a-leaf-02 | port 3 は自分の ethernet-1/3 の先にいると知っている |
| TRex port 3 | 送られたときと同じ形で受け取りたい |

## 困る 1 と 2 を解くために、3 つの仕組みを 1 つずつ足します

- 仕組み 1: IS-IS。leaf 本体から leaf 本体へ、spine を通って IP で届く経路表を自動で作る
- 仕組み 2: BGP EVPN。「port 3 の MAC アドレスは a-leaf-02 の先」と leaf 同士が教え合う。困る 1 が解ける
- 仕組み 3: VXLAN。元のパケットの前に a-leaf-02 宛ての IP ヘッダーを付け足して、spine に IP で運ばせる。困る 2 が解ける

## 仕組み 1: IS-IS は、スイッチ同士が経路表を自動で作り合う仕組みです

各スイッチは本体のアドレス（ループバック）を持ちます。IS-IS が作った dc1-a-leaf-01 の経路表は次の形です。

| 宛先（本体のアドレス） | 出るポート | 次のスイッチ |
|---|---|---|
| 10.255.0.1（spine-01） | ethernet-1/1 | spine-01 |
| 10.255.0.2（spine-02） | ethernet-1/2 | spine-02 |
| 10.255.2.2（a-leaf-02） | 1/1 と 1/2 | spine-01 か 02（同じ長さ） |
| 10.255.1.1 / .2（s-leaf） | 1/1 と 1/2 | spine-01 か 02 |

::: notes
- 本体のアドレス: spine は 10.255.0.1 / .2、WAN 側 leaf は 10.255.1.1 / .2、DC 側 leaf は 10.255.2.1 / .2。
- ケーブル 1 本ごとの区間には 172.16.x.y/31 が付いているが、宛先にするのは本体のアドレス。ポートが 1 本切れても本体のアドレスは消えない。
- IS-IS は level 2、point-to-point、インスタンス名 main（app/containerlab/gen_lab.py）。
:::

## IS-IS は、隣に知らせる・計算する・切れたら計算し直す、の 3 手順で経路表を作ります

- 1 隣に知らせる: 「自分のアドレスと、どのポートの先にどのスイッチがいるか」を隣へ送る。6 台全部が全員分を持つまで繰り返す
- 2 経路を計算する: 集まった「誰と誰がつながっているか」から、宛先ごとに最短でどのポートから出るかを計算して表に書く
- 3 回線が切れたら: 隣に知らせて全員が計算し直す。a-leaf-01 と spine-01 の間が切れると 1/1 の行が消え、spine-02 経由だけになる
- これで leaf 本体同士が IP で届く。この土台の層を underlay（アンダーレイ）と呼ぶ

::: notes
- この段階ではまだ TRex のパケットは運べない。leaf 本体同士が IP で届く土台ができただけ。
:::

## 仕組み 2: BGP EVPN は、leaf 同士が「どの MAC アドレスがどこにいるか」を教え合う仕組みです

- 1 TRex port 3（MAC bb）が最初のパケットを a-leaf-02 の ethernet-1/3 へ送る
- 2 a-leaf-02 は送信元の MAC アドレスを見て「bb は自分の ethernet-1/3 の先」と表に書く
- 3 a-leaf-02 はそれを BGP で spine に知らせる
- 4 spine はほかの leaf 3 台へそのまま配り直す（ルートリフレクタ）。leaf 同士を全部直接つなぐ代わり
- 5 ほかの leaf は「bb は a-leaf-02（10.255.2.2）の先」と自分の MAC アドレステーブルに書く

::: notes
- BGP は、ルーター同士が「自分はこの宛先を知っている」と知らせ合う仕組み。その BGP で IP の経路ではなく MAC アドレスの居場所を知らせる使い方が EVPN。
- 6 台は同じ組織なので全員が同じ AS 番号 65100 を名乗る。共有する LAN には番号 100（VNI）を付け、同じ番号の leaf 同士だけが MAC アドレスの情報を受け取る。
:::

## 教え合ったあと、dc1-a-leaf-01 の MAC アドレステーブルには、ほかの leaf の先にいる MAC アドレスも載ります

| MAC アドレス | どこにいるか | どう送るか |
|---|---|---|
| port 2 の MAC アドレス | 自分の ethernet-1/3 の先（自分で見て覚えた） | ethernet-1/3 へそのまま送る |
| port 3 の MAC アドレス bb | a-leaf-02（10.255.2.2）の先（EVPN で教わった） | 10.255.2.2 宛ての IP ヘッダーを付けて送る（仕組み 3） |
| port 0 の MAC アドレス | s-leaf-01（10.255.1.1）の先（EVPN で教わった） | 10.255.1.1 宛ての IP ヘッダーを付けて送る |

::: notes
- 10.255.2.2 への送り方は仕組み 1 の経路表に書いてある。
- iBGP AS 65100、EVPN だけ、ループバック同士で張る。spine が route reflector で cluster-id は自分のループバック。
- mac-vrf macvrf-100: EVI 100、VNI 100、route-target 65100:100。
:::

## 仕組み 3: VXLAN は、元のパケットの前に IP のヘッダーを付け足して、leaf から leaf へ運ぶ仕組みです

a-leaf-01 は、TRex port 2 が送った元のパケットの前に、次の部分を付け足します（カプセル化）。

| パケットの部分 | 中身と意味 |
|---|---|
| 宛先 IP 10.255.2.2（付け足し） | 仕組み 2 で教わった、bb がいる a-leaf-02 本体のアドレス |
| 送信元 IP 10.255.2.1（付け足し） | 付け足した a-leaf-01 本体のアドレス |
| UDP 4789（付け足し） | 「VXLAN のパケットだ」と分かるための決まった番号 |
| VNI 100（付け足し） | どの LAN か。仕組み 2 と同じ LAN の番号 |
| 元のパケット | 宛先 MAC bb、送信元 MAC aa、宛先 IP 10.100.0.14。そのまま入る |

## VXLAN では、leaf が付け足し、spine が外側だけ見て運び、leaf が外します

- 1 a-leaf-01 が付け足す: 表で引いた bb の居場所 10.255.2.2 を宛先にした IP ヘッダーを、元のパケットの前に付け足す
- 2 spine は外側だけ見て運ぶ: 外側の宛先 IP 10.255.2.2 だけを見て、仕組み 1 の経路表どおりに a-leaf-02 へ渡す
- 3 a-leaf-02 が外す: 自分宛てで UDP 4789 なので付け足した部分を外し、中の元のパケットを ethernet-1/3 へ送り出す
- ヘッダーを付け足して運ぶこの層を overlay（オーバーレイ）と呼ぶ

## 1 つのパケットは、TRex → leaf → spine → leaf → TRex と 5 段階で届きます

- 1 TRex port 2 が送る: 宛先 MAC アドレスを bb（port 3）にしたパケットを送る。LAN の中の形
- 2 a-leaf-01 が付け足す: 表で bb は 10.255.2.2 の先と分かり、その宛先の IP ヘッダーを付け足す（仕組み 2・3）
- 3 spine が運ぶ: 外側の宛先 10.255.2.2 を経路表で引き、a-leaf-02 へ渡す（仕組み 1）。中は見ない
- 4 a-leaf-02 が外す: 付け足した部分を外し、元のパケットを ethernet-1/3 へ送り出す
- 5 TRex port 3 が受け取る: 送られたときと同じ形で届く。間に 3 台いたことは分からない

## パケットの形が変わるのは、leaf と leaf の間だけです

| 区間 | 宛先 MAC アドレス | 宛先 IP アドレス | 付け足したヘッダー（仕組み 3） |
|---|---|---|---|
| port 2 → a-leaf-01 | bb | 10.100.0.14 | なし |
| a-leaf-01 → spine → a-leaf-02 | bb（中にある。spine は見ない） | 10.100.0.14（中） | 外側に 宛先 IP 10.255.2.2、UDP 4789、VNI 100 |
| a-leaf-02 → port 3 | bb | 10.100.0.14 | なし（外した）。送られたときと同じ形 |

::: notes
- spine-01 経由と spine-02 経由は同じ長さなので、leaf が組ごとに 2 本へ振り分ける（ECMP）。1 本切れればもう一方だけになる。
- 相手の MAC アドレスを聞く ARP は LAN 全体宛てなので、a-leaf-01 は同じ LAN 番号 100 の leaf 全部へ複製して送る（ingress replication）。返事が来れば以後は 1 対 1。
- port 0 ↔ port 1 は s-leaf-01 と s-leaf-02 の間で同じ 5 段階。4 台の leaf 全部が 1 つの LAN。
:::

# 見る・替える・まとめ

スイッチが起きたことを知らせる 3 つの経路、SR-MPLS への差し替え、覚えておくこと。

## 6 台のスイッチで起きたことは、3 つの経路で lab の外へ送られます

| 経路 | 送られるもの | 受け取る側 |
|---|---|---|
| SNMP トラップ | 「ポートが落ちた」などの出来事。スイッチが送る | Telegraf がキューへ |
| syslog | スイッチのログ 1 行ずつ。スイッチが送る | syslog-ng がキューへ |
| gNMI | 通信量や BGP の状態。外から定期的に取りに行く | gnmic がキューへ |

- キュー: 届いたものを順にため、読む側が自分のペースで取り出す場所（AWS の MSK）
- そのあと: 取り出して整え、検索・グラフ・保存・アラートの仕組みへ配る
- スイッチは決まった宛先に送るだけ。lab の EC2 が AWS の受け口へ転送する

::: notes
- SNMP trap 162/udp → Telegraf → MSK の traps。syslog 5140/udp → syslog-ng → logs。gNMI 57400 ← gnmic → gnmi（状態の変化）と metrics（60 秒ごとの数字）。
- 宛先 203.0.113.1 は lab の EC2 で、iptables の DNAT で NLB へ転送する（docs/pipeline.md）。
- 後ろは Spark → OpenSearch / Prometheus / S3 Tables / Splunk、アラートは SNS → Lambda → Neptune。
:::

## 依頼にあった SR-MPLS は、機種とライセンスの都合で VXLAN に置き換えています

SR-MPLS は仕組み 3 で付け足すヘッダーを別の種類にする話で、仕組み 1 と 2 はそのまま使います。

| 項目 | いま: VXLAN | 依頼: SR-MPLS |
|---|---|---|
| 付け足すもの | IP のヘッダー（宛先は leaf 本体） | 短い番号（ラベル） |
| spine の仕事 | 経路表を引く IP ルーター | ラベルを見て回すだけ |
| 機種 | ixr-d2l（ライセンス不要） | ixr-6e とライセンスが要る |

## SR-MPLS に替えても、変わるのは leaf の付け足す設定だけです

- 手元に機種とライセンスがないので、まず VXLAN で全体を通すと「lab を IS-IS と TRex で組む（011）」で決めた
- 替えるときは、生成スクリプトで機種とライセンスを指定し直し、leaf の「ヘッダーを付け足す」設定を替える
- スイッチの並び・ケーブル・IS-IS・BGP EVPN・TRex・監視の 3 経路は変わらない

::: notes
- 2026-10-08 の依頼では「ISIS / SR-MPLS」の構成が挙がっていた。
- docs/cycles/011-lab-isis-trex-x86/design.md。gen_lab.py の type を ixr-6e にし license を付ける。
- Neptune の構成図は vtep を SR のラベルと読み替えるだけで、id と edge は変えない（docs/data-stores.md）。

## 覚えておくことは 3 つです

- スイッチ同士は IP で運ぶ。だから a-leaf-01 と a-leaf-02 の TRex 側のポートは、そのままでは同じ LAN にならない
- IS-IS で経路表を作り、BGP EVPN で MAC アドレスの居場所を教え合い、VXLAN で IP のヘッダーを付け足して運ぶ。leaf が付け足し、spine が運び、leaf が外す
- SR-MPLS は付け足すものがラベルに変わるだけ。機種とライセンスがそろったら替える。監視の 3 経路はそのまま
