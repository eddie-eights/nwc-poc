# Cycle 004 splunk-indexer-cluster 設計の経緯

## Round 0（2026-10-04）要件を詰めた

きっかけ: ユーザー「いまって splunk だけクラスター化できていないよね？ splunk をクラスター化したい」。

| 質問 | 推奨 | ユーザーの答え |
|---|---|---|
| Q1 クラスターの範囲（indexer だけか、search head もか） | indexer だけ。manager 1 + indexer 2 + search head 1 | 推奨どおり |
| Q2 Spark からの入口（Cloud Map の DNS か、NLB か） | Cloud Map の DNS | 推奨どおり |
| Q3 index の置き場（タスクの中か、EFS か） | タスクの中のまま | 推奨どおり |
| Q4 切り替え（いつもクラスターか、環境変数か） | 環境変数 `SPLUNK_CLUSTER`、既定は 1 台 | 推奨どおり |
| Q5 順番 | 002 が main に入ってから。003 と並行でよい | 推奨どおり |

ユーザーの言葉: 「全部推奨どおりで進めて。やりたいことは格納してるデータが冗長化されて入ればいい」。

この言葉から決めたこと:

- 目的は「格納したデータの冗長化」の 1 つ。検証の中心を「indexer を 1 台止めても、入れた件数が全部検索できる」に置いた。
- search head の冗長化、AZ をまたぐ配置、EFS は目的の外なので入れない。

## 2026-10-04 やると決まった

ユーザー「splunk をクラスターにするけど、規定は 1 台でいい」。

- ヒアリング（docs/hearing.md の項目 1）の答えを待たずに、このサイクルをやる。
- 既定は 1 台のまま。設計の `SPLUNK_CLUSTER`（既定 0）と同じなので、設計は変えない。

## 2026-10-04 切り替えを `SPLUNK_AZ_NUM` にした

ユーザーの決定「リソースごとに `<リソース>_AZ_NUM=1|2|3` で冗長化の度合いを選ぶ。既定は 1」に合わせた。

- `SPLUNK_CLUSTER`（0 / 1）はやめ、`SPLUNK_AZ_NUM`（1 / 2 / 3、既定 1）にした。1 は今の 1 台、2 と 3 は indexer を AZ ごとに 1 台ずつ置くクラスター。
- 「AZ をまたぐ配置は目的の外」を取り消した。indexer は AZ をまたぐ。manager と search head は 1 つ目の AZ のまま。
- 複製の数と、検索できる複製の数は、indexer の数と同じにした。
- クラスターでは index は `main` だけ（`SPLUNK_INDEX` が空でなければ止める）。
- SG の `splunk → splunk`（8089、9887）はいつも作る。base/core は `SPLUNK_AZ_NUM` を知らない層のため。
- 実装を始める条件に `feat/splunk-boto3` と `feat/az-num` を足した。
- この節の中身は、こちら（設計の役）が決めてユーザーに報告したもの。ユーザーからの異論は出ていない。

## 2026-10-04 手元の確認の結果を反映した

エンジニアセッションが Docker の 4 台で確かめた。7 項目は期待どおり。新しい問題が 1 つ。

- 新しい問題: indexer が前と同じ IP で入れ替わると、search head が検索できず（401）、アラートが黙って落ちる。
- 手当ての候補は A（search head のヘルスチェックで突き合わせ）、B（up.sh で 1 回確かめる）、C（GUID を固定）。エンジニアのおすすめは A。
- こちら（設計の役）が A と B の両方に決めた。C はやらない。ユーザーには報告した（異論があれば変える）。
- `indexes.conf` は書かない、`SPLUNK_INDEXER_URL` は付けない、indexer に `stopTimeout = 120`、SG に 9997 を足す。
- 004 とは別に切り出すもの: 存在しない index 宛ての HEC が 200 を返して捨てられる件、`tests/check_splunk_image.py` が Docker の volume を残す件。

## 2026-10-04 案 C（GUID を台ごとに固定）を手元で確かめた

ユーザーの指示（「C ができれば簡単だよね、検証して」）で、エンジニアが手元の Docker の 4 台で確かめた。結果は不合格。A と B のままにする。

| # | 確かめたこと | 結果 | 見えたこと |
|---|---|---|---|
| 1 | 同じ IP・同じ GUID で入れ替え | 不合格 | 15 分たっても 401。新しい台の `distServerKeys` が空。新しく入れた 100 件は 0 件、link down の通知も出ない。もとの 1000 件が黙って 500 件に減った（その間 manager は RF / SF を met と表示） |
| 2 | 同じ GUID・別の IP | 不合格 | manager が参加を断る行が 25 分で 33 回。RF / SF は NO のまま。参加前に受けた 174 件は消えた。search head の件数は 2〜3 倍に重複 |
| 3 | manager の側（空の台が同じ GUID で来る） | 不合格 | bucket の ID がぶつかり、空の新しい台が勝って、ほかの台の古いコピーが切り詰められた |
| 4 | 同じ GUID の 2 台が同時に動く | 不合格 | manager は新しい台を断り続けるが、コンテナは healthy。古い台を先に止めても、3 と同じ衝突が起きた。RF / SF は 8 分 NO のままで、hot bucket を手で roll して戻った |
| 5 | GUID を入れる | 合格 | 入口で `/opt/splunk-etc/instance.cfg` に書けば残る。値は AZ の番号から作る uuid5 で足りる |

- 未確認: ECS で、新しいタスクがクラスターに入る前に HEC を受けるか。受けない場合に、別の IP で main の衝突が起きないか。待ち行列が詰まった台が `stopTimeout` 120 で SIGKILL になるまでの動き。
- 分かったこと: 401 の原因は GUID ではなく鍵。search head に peer を登録し直させる処置（A の入れ替え）が要るのは、C を入れても同じ。

## 2026-10-05 実装の前に、設計と現物の食い違いを直した

エンジニアの指摘を受けて、設計の役が決めた。

- 合言葉の環境変数は `SPLUNK_IDXC_PASS4SYMMKEY`（10.4.3 の実物）。`SPLUNK_IDXC_SECRET` は推測だった。
- 変更対象ファイルの表から `indexes.conf` を外し、SG とテストの節に 9997 を足した（前に決めた内容に、表が追いついていなかった）。
- いまのテスト（splunk 宛ての 8089 を禁じる検査、「キーがまだ無いもの: Splunk…」の行）は、テストのほうを直す。
- B の経路: A のスクリプトが判定を標準出力に書き、up.sh が CloudWatch Logs から読む。やらない案は、ECS Exec（終了コードが戻らない。IAM と session-manager-plugin が要る。標準出力に書けないときの控え）と、B をやめる（デプロイの直後に食い違っても up.sh が成功で終わる）。
- indexer の AZ: 1 つのサービスのまま、Fargate の振り分けに任せる（保証ではない）。up.sh が同じ AZ に 2 台いたら注意を出す。やらない案は、AZ ごとにサービスを分ける（全部のサービスが同時に入れ替わる）。
- 参加前の HEC: Cloud Map の `health_check_custom_config` で防ぐ。indexer のヘルスチェックに manager の確認は入れない。
- `stopTimeout` 120 秒で止まりきらないことは受け入れる。
- 未確認: 参加前に受けた分が、複製されない単独の bucket になるか（エンジニアの推測）。

## 却下した案

| 案 | やめた理由 |
|---|---|
| いまのタスクの `desired_count` を 2 にする | 2 台が別々の index を持つだけで、複製されない。保存済みサーチも 2 台で動き、アラートが二重に出る |
| 1 台のまま index を EFS に置く | タスクが落ちてもデータは残るが、複製ではない。落ちている間は受けられない。ユーザーの依頼は「クラスター化」 |
| search head クラスター（3 台 + deployer） | 合計 7 台になる。データの冗長化には要らない |
| indexer に forwarder を挟む | Spark は HEC に直接書いている。HEC は indexer が直接受けられるので、台を増やす理由が無い |
| NLB | 部品が増える。DNS の片寄りはデータの冗長化に影響しない |
| indexer ごとにイメージを分ける | 同じイメージを `SPLUNK_ROLE` で使い分けられる。ECR とビルドを増やさない |

## 2026-10-05 入れ替えた直後にもう 1 台を止めると、検索が 0 件になる

- エンジニアの報告: 手元の確認（idx1 を別の IP で入れ替え → HEALTHY と RF/SF met → すぐ idx2 を止める）で、search head の件数が 300 秒あまり 0 になった（3 回中 3 回）。データは消えず、manager が世代を確定し直すと 1000 に戻る。そのあいだアラートの検索は 0 件のまま成功する。
- 原因（エンジニアが manager のログで特定）: 止める台にある、複製先の無い hot の bucket が primary の付け替えを止め、世代の確定が失敗する。再試行は `commit_retry_time`（既定 300 秒）のあと。
- 決めたこと: PoC では受け入れて、リスク 11 に書く。実装（2945470）は main に入れる。クラスターは `SPLUNK_AZ_NUM` を 2 か 3 にしたときだけなので、既定の 1 台の構成には影響しない。
- 続き: 止める前の `splunk offline` と `commit_retry_time` の短縮を、エンジニアに手元で確かめてもらう。効くなら入れる。
- やらない案: indexer のヘルスチェックを「クラスターが落ち着くまで HEALTHY にしない」に変える。止める側の hot の bucket が原因なので、入ってくる側を待たせても効かない見込み。
- 結果（同日）: `splunk offline` が効いた。エンジニアが 3 回走らせて 3 回とも 0 件の時間が出ず、実装（1d7d8b1）を main に入れた。`commitGenerationFailure` は offline の始めに 1 回出るが、約 0.4 秒後に確定し直す。`commit_retry_time` の短縮は、条件（offline で消えない、または 120 秒を超える）に当たらなかったので試していない。リスク 11 を「手当てを入れた。予期しない停止では残る」に書き直した。
