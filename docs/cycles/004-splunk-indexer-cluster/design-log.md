# Cycle 004 splunk-indexer-cluster 設計の経緯

## Round 0（2026-10-04）要件を詰めた

きっかけ: ユーザー「いまって splunk だけクラスター化できていないよね？ splunk をクラスター化したい」。

| 質問 | 推奨 | ユーザーの答え |
|---|---|---|
| Q1 クラスターの範囲（indexer だけか、search head もか） | indexer だけ。manager 1 + indexer 2 + search head 1 | 推奨どおり |
| Q2 Spark からの入口（Cloud Map の DNS か、NLB か） | Cloud Map の DNS | 推奨どおり |
| Q3 index の置き場（タスクの中か、EFS か） | タスクの中のまま | 推奨どおり |
| Q4 切り替え（いつもクラスターか、環境変数か） | 環境変数 `SPLUNK_CLUSTER`、既定は 1 台 | 推奨どおり |
| Q5 順番 | 002 が main に入ってから。003 と並行でよい | 推奨どおり |

ユーザーの言葉: 「全部推奨どおりで進めて。やりたいことは格納してるデータが冗長化されて入ればいい」。

この言葉から決めたこと:

- 目的は「格納したデータの冗長化」の 1 つ。検証の中心を「indexer を 1 台止めても、入れた件数が全部検索できる」に置いた。
- search head の冗長化、AZ をまたぐ配置、EFS は目的の外なので入れない。

## 2026-10-04 やると決まった

ユーザー「splunk をクラスターにするけど、規定は 1 台でいい」。

- ヒアリング（docs/hearing.md の項目 1）の答えを待たずに、このサイクルをやる。
- 既定は 1 台のまま。設計の `SPLUNK_CLUSTER`（既定 0）と同じなので、設計は変えない。

## 却下した案

| 案 | やめた理由 |
|---|---|
| いまのタスクの `desired_count` を 2 にする | 2 台が別々の index を持つだけで、複製されない。保存済みサーチも 2 台で動き、アラートが二重に出る |
| 1 台のまま index を EFS に置く | タスクが落ちてもデータは残るが、複製ではない。落ちている間は受けられない。ユーザーの依頼は「クラスター化」 |
| search head クラスター（3 台 + deployer） | 合計 7 台になる。データの冗長化には要らない |
| indexer に forwarder を挟む | Spark は HEC に直接書いている。HEC は indexer が直接受けられるので、台を増やす理由が無い |
| NLB | 部品が増える。DNS の片寄りはデータの冗長化に影響しない |
| indexer ごとにイメージを分ける | 同じイメージを `SPLUNK_ROLE` で使い分けられる。ECR とビルドを増やさない |
