### Neptune Analytics で分析するときの質問

- ユーザーの質問: 分析のときに障害情報や修復案も必要になるなら、プロパティとして入れたほうがよいか。
- 答え: 正は S3 Tables に置く。グラフで分析したくなったら、`alert_events` / `proposal_events` から写しを頂点と辺として載せる。機器のプロパティに入れると、履歴が持てず、最新しか残らない。
- ユーザーの回答: 「正は S3 Tables、必要なときに写しを載せるで OK」。このサイクルではやらない。

### 途中で直した誤り

- 「エージェントが承認を書く」と言ったのは誤り。`decide` を呼ぶのは Web の承認タブだけで、ツールには出していない。
- 「Web から Temporal に直接シグナルを送る」案を出したが、Temporal はタスクの中の `localhost:7233` でしか待っていない。SQS を通す形に変えた。

### 却下した案

- **Web から Temporal に直接シグナルを送る。** Temporal の口を VPC に開けることになる。「画面と Temporal を直接つながない」という今の線も変わる。
- **Web が `proposal_events` に承認の行を直接書く。** 書く人が 2 人になり、二重の承認を防ぐ条件付きの書き込みが Iceberg には無い。
- **「いま」用のテーブル `proposals` を別に作る。** Iceberg の行の書き換えが要る。履歴と 2 か所に書く形も残る。
- **Neptune の頂点も残し、プロパティか辺で分析に使う。** 同じ内容を 2 か所に書く今の形が残る。分析が要るときに写しを載せれば足りる。
- **決定のキューを分ける。** 待つループが 2 つになる。エンドポイントと Deny は共用で足りる。
- **順番を `event_time` で決める。** 秒なので、同じ秒に 2 行入ると順番が決まらない。`seq` を足した。
- **起動のときに古い pending を掃除する。** 今もある穴で、範囲が広がる。リスクに書いて残した。

## 2026-10-05 Runtime の代替実行で返るもの

- エンジニアの指摘: 「代替実行では『まだ配備されていない』が返る」と「Web の設定は SSM のパラメータで渡す」は両立しない。Runtime も `parameter/<prefix>/*` を読めるので、設定を引けて、Athena の AccessDenied になる。

## 2026-10-05 Round 1 のセルフレビューで出た 3 件

エンジニアが実装（4d4d5d7）のセルフレビューで、設計の側で決めることを 3 件挙げた。設計の役が決めた（ユーザーには報告した。異論があれば変える）。

- 決定の順番（2 人が数秒差で却下と承認を押すと、先に届いたほうが効き、負けたほうは何も残らない）
  - 決めたこと: 効かなかった決定を `ignored` の行として残す。順番は変えない。
  - 理由: 困るのは「順番が逆になること」より「負けた決定が跡形もなく消えること」。行に残せば、あとから誰が何を押したかを追える。変更は worker と rules だけで済む。
  - やらない案 1: FIFO キュー。キューに届いた順は守られるが、2 つのブラウザから数秒差で送られたものの「押した順」までは保証できない。キューの作り直し、MessageGroupId、重複排除の ID が要り、変更が広い。
  - やらない案 2: 却下を承認より優先する。承認が先に効いて実行が始まったあとの却下は、どのみち止められない。運用の決まりを変える話なので、このサイクルでは入れない。
- Temporal の履歴が消えたときに救える範囲
  - 決めたこと: リスク 5 に範囲を書く（閉じられるのは pending だけ。approved / applied で止まったものは残る）。起動のときに `failed` で閉じる処理は入れない。
  - 理由: 「起動のときの掃除は入れない」という前の決定と同じ扱い。
- リスク 9 の文言
  - 決めたこと: 「失敗する」を、エンジニアが再現した動き（追記は成功し、null の入った行が入る）に直す。「analytics を作り直したら workflow も apply」をリスク 9 に書き、実装が main に入ったら docs（troubleshooting.md）にも書く。
- あわせて: `'` を含む `target` の修復案は決められないことを、リスク 11 に足した。

## 2026-10-05 承認待ちが終わったあとに届いた決定

- エンジニアの指摘: 時間切れのあとも、ワークフローは解消の通知を待って最長 24 時間残る。そのあいだに決定が届いたときの扱いが設計に無い。いまの作りだと、その決定が「効いた決定」として控えられ、そのあとに届く決定に「先に承認が決まっていた」という誤った `ignored` の行が付く。
- 決めたこと: 承認待ちが決定なしで終わったあと（`expired` / `obsolete`）に届いた決定は、行にしない。worker のログに 1 行出す。効いた決定としても控えない。
- 理由: 「ワークフローが終わったあとに届いた決定はログだけ」と同じ扱いにそろえる。`ignored` の行は「効いた決定に負けた」ことの記録なので、効いた決定が無いときに書くと中身が嘘になる。
- やらない案: `ignored` の行として残し、`detail` を「時間切れのあとに届いた」にする。`ignored` の意味が 2 つになり、読む側（画面の履歴、Athena の集計）が `detail` の文面で見分けることになる。
