### Neptune Analytics で分析するときの質問

- ユーザーの質問: 分析のときに障害情報や修復案も必要になるなら、プロパティとして入れたほうがよいか。
- 答え: 正は S3 Tables に置く。グラフで分析したくなったら、`alert_events` / `proposal_events` から写しを頂点と辺として載せる。機器のプロパティに入れると、履歴が持てず、最新しか残らない。
- ユーザーの回答: 「正は S3 Tables、必要なときに写しを載せるで OK」。このサイクルではやらない。

### 途中で直した誤り

- 「エージェントが承認を書く」と言ったのは誤り。`decide` を呼ぶのは Web の承認タブだけで、ツールには出していない。
- 「Web から Temporal に直接シグナルを送る」案を出したが、Temporal はタスクの中の `localhost:7233` でしか待っていない。SQS を通す形に変えた。

### 却下した案

- **Web から Temporal に直接シグナルを送る。** Temporal の口を VPC に開けることになる。「画面と Temporal を直接つながない」という今の線も変わる。
- **Web が `proposal_events` に承認の行を直接書く。** 書く人が 2 人になり、二重の承認を防ぐ条件付きの書き込みが Iceberg には無い。
- **「いま」用のテーブル `proposals` を別に作る。** Iceberg の行の書き換えが要る。履歴と 2 か所に書く形も残る。
- **Neptune の頂点も残し、プロパティか辺で分析に使う。** 同じ内容を 2 か所に書く今の形が残る。分析が要るときに写しを載せれば足りる。
- **決定のキューを分ける。** 待つループが 2 つになる。エンドポイントと Deny は共用で足りる。
- **順番を `event_time` で決める。** 秒なので、同じ秒に 2 行入ると順番が決まらない。`seq` を足した。
- **起動のときに古い pending を掃除する。** 今もある穴で、範囲が広がる。リスクに書いて残した。
