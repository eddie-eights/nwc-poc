## 検証の手筋

- AWS の外から VPC の中へは入れない（閉域）。Web の EC2 の上で `scratchpad/ssm-run.sh <instance> <script>` を使い、base64 で送ったスクリプトを AWS-RunShellScript で打った。
- パスワードとトークンは EC2 の上で `aws ssm get-parameter --with-decryption` で取り、シェル変数に入れた。出力には出していない。
- Grafana は `admin` で、データソースの汎用のプロキシ（`/api/datasources/proxy/uid/<uid>/...`）を使った。
  - VictoriaMetrics: `/api/v1/query`
  - OpenSearch: `_cluster/health`、`_cat/nodes`、`snmp-logs*/_count`
  - マネージド版（AMP / OpenSearch Serverless）と違い、OSS 版は汎用のプロキシで値が返った（署名が要らないため）。
- Kafka は Kafbat UI の API（`http://kafka-ui.<名前空間>:8080/api/clusters/...`）で見た。クラスター名は `efukuda-nwc-oss-stream`。
  - 注記（2026-10-09、Kafbat UI を Web の EC2 に移した残りを直す（014））: この検証のあと、Kafbat UI を Web の EC2 に同居させる（010）で、Kafbat UI は Web の EC2 の Docker（`127.0.0.1:8082`）に移り、クラスター名（REST の `/api/clusters/{name}/…` の識別子）は `<prefix>`（この環境なら `efukuda-nwc-oss`）になった。いまの環境で同じことをするなら、Web の EC2 の上で `http://127.0.0.1:8082/api/clusters/efukuda-nwc-oss/...` を叩く。
- Splunk は、マネージド版と同じく `cval` でログインし、CSRF の cookie を `X-Splunk-Form-Key` に入れて `services/search/jobs/export` でサーチした。
- Neo4j と修復案は、Web の EC2 の上の Web アプリのモジュール（`graph` / `topology` / `proposals` / `incident_view`）を python3.13 で呼んで見た。
- Nautobot は REST API（`/api/dcim/devices/`、`/api/extras/jobs/`、`/api/extras/job-results/`）を Web の EC2 の上から叩いた。
  - `job-results` は `?ordering=-date_created` を付けると HTTP 400 になったので、`?limit=200&depth=1` で取って手元で並べた。
- エージェントは手元から `aws bedrock-agentcore invoke-agent-runtime` で呼び、Runtime のロググループで道具の呼び出しを見た。
- ログは CloudWatch Logs の `filter-log-events` で見た。
  - worker: `/ecs/efukuda-nwc-oss-workflow`
  - Lambda: `/aws/lambda/efukuda-nwc-oss-graph-status`、`/aws/lambda/efukuda-nwc-oss-tools`
- S3 Tables は Athena（ワークグループ `efukuda-nwc-oss-history`）で `"s3tablescatalog/efukuda-nwc-oss-tables".netops.raw_telemetry` を数えた。
- タスクの停止は `aws ecs stop-task`（reason `verify-oss-20261008-chaos`）。
- 消えたことの確認は、タグの API（down.sh の 6.）を当てにせず、サービスごとの API で見た（`scratchpad/oss/gone-oss.sh`）。

## 不具合

1. `oss/ops/roll-nodes.sh` は、標準入力が端末でないと動かない。
   - `roll_exec` の `aws ecs execute-command --interactive` は、端末の無いシェル（CI、`nohup`、`< /dev/null`、エージェントのシェル）では `Cannot perform start session: EOF` で、タスクの中のコマンドの出力が返る前に切れる。
   - 切れても `roll_health.py` は「urp の節が無い」と見て、5 分待ってから `Kafka が入れ替える前から健全でない` で止まる。Kafka は健全だったので、文面が原因を指さない。
   - 何も入れ替えずに止まるので、壊れはしない。
   - 直し方の案: 入れ替える台があるときに `[ -t 0 ]` を見て、端末が無ければ `script -q /dev/null` で包むか、「端末から打つ／`OSS_ROLL=0`」と案内して止める。`roll_health.py` も `Cannot perform start session` を見分けて出す。
2. Neo4j のタスクが入れ替わると、変更履歴（`change` ノード）が消える。`ops/sync-graph.sh --oss` は物理層と IP 層を戻すが、変更履歴は 0 件のまま。
   - Nautobot の手で打つ Job を打つと戻った（19 件）。
   - 不具合というより、戻す手順が 2 段あることが書かれていない（下の「docs のずれ」4）。
3. `oss/terraform/base/ecr` の state が無いまま ECR だけ残ったとき、`aws_ecr_repository.pipeline[...]` を 1 本ずつ import すると `Error: Invalid index` で落ちる。
   - outputs.tf の 6 つの output が `aws_ecr_repository.pipeline["<key>"]` を直接引いていて、import の途中（ほかのキーがまだ state に無い）で評価に失敗する。
   - 今回は一時的な override で `try()` にして通した。`KEEP_ECR=1` で残して state を失う流れ（worktree を消す）は起こりやすいので、outputs.tf を `try()` にするか、import の手順を `oss/ops/` に置くのがよい。
4. Nautobot の JobHook で、ある機器の最初の変更履歴の detail が、全部の項目を「- → -」と並べる（`asset_tag: - → -、clusters: - → []、comments: - → -、…`）。
   - その機器の変更前の値（prechange）が無いため。2 件目からは `status: Maintenance → Active` のように差分だけになった。
   - 読む人には意味の無い行が並ぶ。prechange が無いときは、変わった値だけ（または「作成／初回」）を出すのがよい。
5. `ops/down-common.sh` の `destroy_base_core`（115〜116 行目）は、Runtime の ENI を探す VPC を `describe-vpcs --filters Name=tag:Name,Values=$PREFIX-vpc --query 'Vpcs[0].VpcId'` で引く。
   - 同じ名前の VPC が 2 つあると、state の VPC でない方を引くことがある。今回は古い `vpc-01e7940d673125453` を引き、今回の VPC の `agentic_ai` の ENI を見落とした。
   - そのため「VPC 一式を残して他を消す（rc=0）」の道に入らず、base/core を全部消しにいき、SG の削除の待ちを 3 回繰り返して rc=1、1 時間 41 分かかった。
   - 名前の重なりは、state を失って up.sh が新しい VPC を作ると起きる（「state の扱い」）。
   - 直し方の案: `tf base/core state show aws_vpc.this` の id を先に使い、取れないときだけタグで引く。タグで引くなら全部の VPC を見る（`Vpcs[].VpcId`）。

   - 1 台ずつの入れ替え（既定の `OSS_ROLL=1`）は、端末から打たないと止まる（「不具合」1）。
6. state を失ったときの扱い。
   - `design.md` は、残った VPC を「消し切るなら数時間おいて down.sh を打ち直す」とし、残った ECR は「次の up.sh でイメージの写しを飛ばすため」としている。
   - どちらも、同じ state から打つことが前提。state は up.sh を打った worktree にしか無い。worktree が消えると、ECR は import が要り（「不具合」3）、VPC は使い回されずに新しく作られる（今回 `vpc-0128b41b696d4e6d7`）。
   - 残った VPC が溜まっていき、名前が重なって down.sh が VPC を取り違える（「不具合」5）。
   - 今回の VPC も、この worktree を消す前に打ち直さないと、また state の無い VPC が残る。

## 検査の手筋のずれ（docs ではなく、依頼の手順）

- 前回の手筋（`scratchpad/web-check2.sh`）の Splunk のサーチと Kafbat UI の API の叩き方は古かった。
  - Splunk は、マネージド版の記録の「検証の手筋」と同じく `cval` と CSRF の cookie が要る。
  - Kafbat UI はクラスター名 `efukuda-nwc-oss-stream` で引く。
    - 注記（2026-10-09、014）: 010 からはクラスター名が `<prefix>`（`efukuda-nwc-oss`）で、場所は Web の EC2 の `127.0.0.1:8082`。上の「検証の手筋」の注記と同じ。
- Nautobot の `job-results` は `ordering` を付けると 400（上の「検証の手筋」）。
- 1 台ずつの入れ替えを確かめるには、`script -q /dev/null` で疑似端末を付け、`AWS_PAGER=""` で up.sh を打つ。
- down.sh の 6.（タグの API）の件数は当てにならない。サービスごとの API で数える。
